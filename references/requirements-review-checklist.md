# 需求一致性与正反路径

用于文档核对、指定功能的条件与边界审查。没有文档时，以用户描述和已证实的业务约束为依据；缺失依据明确记录，继续可独立完成的检查。

<a id="r1-requirements"></a>
## R1 需求拆解与依据

- 将文档拆成可观察、可独立判断的条款，保留章节／页码／段落等来源；图示、表格、脚注中的条件和例外也属于需求。
- 对每条记录：适用对象与模式、前置条件、触发、允许行为、禁止行为、例外／优先级、预期结果、实现证据及结论。短需求可简记，不能省掉影响判断的条件。
- 用户明确补充优先；文档版本或规则冲突无法消解时列出冲突，继续不受影响的审查。
- 不把未实现、未找到、需求未定义混为一谈；不以现有代码、同类游戏或个人经验反推策划意图。

<a id="r2-conditions"></a>
## R2 条件与正反路径

对影响结果的条件建立紧凑决策记录，覆盖实际适用的维度：

| 维度 | 核对内容 |
|---|---|
| 允许 | 条件满足时是否可达、执行次数及结果正确；资源、进度、展示一致 |
| 禁止 | 条件不满足时是否拒绝；拒绝前后是否已扣费、记进度、发奖励、改存档或留下锁 |
| 例外与优先级 | 多条件同时满足或冲突时采用哪条规则；特殊模式是否有明确例外 |
| 边界 | 零、空、阈值恰好相等、前后相邻值、首尾阶段、上限、异常输入 |
| 取消与失败 | 取消、失败、超时、提前返回后哪些变化应保留、恢复或补偿 |
| 重复与替代入口 | 连点、重入、重试、通知或其他界面进入时，是否绕过同一业务校验 |

- UI 隐藏或按钮置灰只能证明该入口受限；按实际代码检查其他可达入口。
- 对条件独立改变并观察结果；根据依赖关系补充冲突组合，不机械排列全部条件。
- “禁止行为不发生”不等于发生后无提示，也不等于事后恢复了界面；检查真实业务副作用。
- 结算、扣除涉及资源时补查 [A2 资源与奖励](activity-reward-review-checklist.md#a2-rewards)；取消或失败后不能继续时补查 [S3 阻塞与恢复](state-machine-review-checklist.md#s3-recovery)。

<a id="r3-traceability"></a>
## R3 双向追踪与影响范围

- **需求到实现**：从入口追踪校验、状态变化、结果及恢复，检查条款是否完全覆盖，是否只在部分来源／模式／阶段实现。
- **实现到需求**：反查相关实现中的额外扣除、奖励、进度变化、分支和限制是否有依据；额外行为先核对上下文，不能一律判错。
- 沿共享状态、事件、公共基类、调度和存储关系检查新功能影响旧流程、旧流程影响新功能的两个方向。
- 宣称“漏实现”前，检查实际注册、调用方、继承／组合、资源绑定、运行时选择和其他可达入口；搜索没有命中只能说明尚未定位。
- 对比旧路径时解释差异的业务意义；历史行为或“其他模块也这样写”不能证明正确。

<a id="r4-results"></a>
## R4 核对结果与未覆盖项

内部跟踪每条结论，报告中在问题列表之后汇总：

| 需求来源／条款 | 预期要点 | 结论 | 实现或问题证据 |
|---|---|---|---|

结论使用：**符合／存在偏差／部分实现／未定位到实现／需求待明确／证据不足**。符合时也注明静态分析或实际验证范围；用问题编号关联缺陷，避免重复整段问题描述。需求待明确只留在本核对结果中，不写入问题台账、不分配编号。

这是需求核对记录，不是测试用例表。相近且结论相同的条款可合并引用，但不能把未核对条款标成符合。未覆盖项说明缺少的代码、数据、环境或外部行为证据及其影响，不笼统写“全部正常”。
