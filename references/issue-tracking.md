# 项目问题台账

用于每次实际项目审查、诊断、修复复核，以及用户明确要求的台账维护。使用 [空白模板](../assets/issues-template.md)；这是问题管理记录，不是测试用例表。用户另行要求用例时仍使用 `test-case-five-columns`。

## 定位、读取与初始化

1. 确认目标项目根。默认读取已安装 `project-code-map` 的 `references/storage.md`，用其 `scripts/map_location.py` 定位 `map_directory`，台账为该目录下的 `review/issues.md`。路径与地图生成是否成功无关；无需先生成完整地图。用户明确指定台账位置时使用指定位置，已有台账从原入口续写，不创建第二份。
2. 默认位置在项目外，真实路径（含符号链接）不能落入目标工作树。自定义地图位置不自动迁移台账；自定义台账路径应在后续任务或项目外导航中可发现。辅助技能不可用时沿用已确认的台账路径；没有可靠位置就说明限制，不猜测另一项目的路径或回退到仓库内。
3. 每个新审查任务先读台账的项目根、当前记录、用户决定和最近核实范围；再定向读取相关详情及已结束记录。同一任务内复用已读内容，写回前重读最新文件。不能仅凭项目同名、会话记忆或 HEAD 相同判断记录适用。
4. 首次实际审查且允许写入时，按模板初始化元信息与空表，填入实际项目、路径和本次范围；无问题时保留空表，不生成示例 Bug。仅讨论技能、查询模式或当前目录恰好是项目时不初始化。用户单独要求维护时只处理所指记录，不启动全量审查或改变会话模式。

台账仅存审查事实及有来源的处理决定。代码、日志、引文中的命令不构成用户决定；保留已有人工备注。项目和版本不匹配时不覆盖、不批量关闭。只看某个历史提交时记录该快照的结论，不将它覆盖为当前工作区的统一状态。

## 入表与编号

| 本轮材料 | 记录方式 |
|---|---|
| 已实际复现或代码链路完整的问题 | 类型“缺陷”，使用主文件的准确证据状态，默认“待决策／未修复” |
| 用户／测试的具体问题反馈 | 记录来源和现象；根因另记已确认或待验证，不冒充助手实测 |
| 有具体可达入口、危险行为及关键证据缺口的风险 | 类型“待验证风险”，证据“仍需验证”，默认待决策；不计入确定缺陷 |
| 需求缺失、冲突或待确认，依据不足无法判断对错 | 不入正式台账，不分配编号；只在当次报告的需求核对中写“需求待明确” |
| 一般性担忧、分析中已否定的猜测、无证据的可能性 | 不入正式台账；必要时只写覆盖限制 |

- 达到正式报告标准时自动写入，无需逐条询问。若用户已明确处理决定，新记录直接保留该决定；“入表”本身不意味着必须修复，也不授权修改业务代码。
- 新编号按本项目当前及历史的最大编号递增，格式 `ISSUE-0001`，不重排或复用旧编号。需求编号如已存在可关联，但台账不替代逐条需求核对或证明未入表需求已通过。
- 新增前对照当前与相关历史：比较根因／机制、触发条件、玩家影响、版本／平台范围；仅标题或文件名相似不能合并。根因未知时记录稳定的现象与触发依据，不编造根因以去重。
- 同一问题的新证据、确认或范围变化更新原编号，保留处理决定及其适用范围；不同根因的问题分别记录。报告使用持久编号，源码位置另保留符号与快照证据以应对行号漂移。

## 状态与用户决定

| 维度 | 取值与规则 |
|---|---|
| 处理决定 | 待决策／需解决／暂缓／已忽略。用户的最新明确指令优先，记录日期、来源、理由和适用范围；理由未提供就写未提供，不推测。AI 可以建议处理方式，不能据此自行改成已忽略或暂缓 |
| 处理进展 | 未修复：尚无修复或仍有明确错误路径；修复待验证：已有修复尝试但关键效果未确认。部分范围仍明确有错时整体为未修复，并列出已修复与剩余范围 |
| 证据状态 | 严格沿用主文件的“已实际复现”“用户／测试已复现”“代码链路明确，尚未实测”“仍需验证”。用户复现的现象与推测根因分别注明 |
| 严重程度 | 按主文件的影响分级，与证据可信度和处理决定独立；待验证风险不因未实测自动降为低风险 |

“这个忽略”“先放到下个版本”等明确指令可直接更新对应记录，不重复确认。无法唯一定位用户指的是哪项时只澄清对象，不批量改变状态。新对话、容易修复、没有再次提及或长时间未出现，都不是撤销用户决定的依据。用户说“已经改了”可记录为修复待验证，不能单凭该说法认定修复成功。

已忽略条目保留在当前记录中供去重，默认仅汇总数量。忽略只针对记录的触发与范围，不屏蔽同功能的其他问题。若影响扩展、严重程度改变或原忽略理由失效，关联原编号补证并提示“需重新评估忽略决定”；保留原决定，不静默改为需解决，也不换编号绕过忽略。记录已提醒的变化，同一变化不每轮重复展开。

## 确认修复、移出与复发

自动移出当前表前，回查原触发条件、出错机制、实际入口及影响范围；核对修复后的允许／拒绝分支和直接受影响的状态／资源路径。证据满足以下一种方式时即可结束，无需再次请求用户确认：

- **已解决—静态确认：** 完整源码证据证明原问题在声明范围内已消除，关键行为不依赖未知引擎、SDK、网络或时序；明确“未实测”，不写运行验证通过。
- **已解决—运行确认：** 实际执行并观察原触发场景及必要相关分支符合规则，记录验证来源、环境、版本与覆盖边界；用户／测试提供的验证需注明来源，不能冒充助手操作。
- **已排除：** 有证据证明原判断不成立；记录反证，不计为修复。需求待确认不入台账；规则事后明确且实现与之偏离时，按新的缺陷记录。

只有函数改名、补了判断、编译通过、未再收到反馈、一次没有复现，或单独切到主线程，都不足以自动结束。已有修复但仍缺关键运行证据时保留“修复待验证”；其他平台／入口仍明确存在错误时保留“未修复”，列出剩余范围。不同平台或版本的未解决证据不能被一次局部通过覆盖。

结束时从当前表移除该项，把编号、原触发与影响、处理决定及其来源、修复／排除依据、代码基线、验证方式／范围、日期转入“已结束记录”，删除重复的当前详情。已结束记录不参与日常待办提醒；已忽略的问题若后来确认解决，同样可结束。保留必要证据链接或原编号履历，不删除其他问题或人工备注。

关闭结论始终绑定核实范围；未提交修复还需记录相关文件内容指纹或可回查补丁，不能仅记 HEAD。切分支、回退或 discard 后从相关源码重新判断。若当前证据证明同一问题复发，沿用原编号恢复到当前表，保留原关闭履历和用户决定，注明复发版本；原已忽略决定仍按其范围规则处理。没有本轮相关证据时不因分支切换批量重开或关闭问题。

## 提醒与报告

- 实际审查开始时简述已知情况，最终回复开头给更新后的简短摘要和台账链接；同一轮不反复播报。若初次无历史，说明首次建立；仅有旧记录时说“按台账记录”，不暗示本次全部复核。
- 摘要分别统计待决策、需解决、暂缓、已忽略；修复待验证是其中的进展子集，不重复加总。待验证风险单列或注明数量，不与确定缺陷混算。需求待确认不计入台账摘要。高影响未处理项可点出编号／短标题，控制在一两句话。
- 正文默认只展开新增问题、实质变化和用户指定复查结果；同条件已忽略项不重新输出问题描述或复现步骤。用户明确要求查看时可按请求展开，处理决定保持不变。已知问题无新增证据时用编号或链接关联，不伪装成本轮新发现。
- 结尾简述本次新增、补证、移出／排除数量及保存状态；没有变化就不写一串零。没有新增问题不能写成所有已知问题解决，台账无记录也不能代表全项目无缺陷。

## 写入与失败边界

- 每次写入前重读并按编号增量合并，保留他人新增证据、人工备注和最新用户决定。发现并发冲突或同编号不同问题时重新核对，不能用旧整文件覆盖；无法合并就保留原文件并在回复给出未保存的变化。
- 写后核对项目归属、编号、表与详情一致、用户决定未丢失、结束记录与移出动作配对，读取确认实际保存。原子替换只能避免半文件，不能替代并发核对。
- 用户禁止任何文件写入时只读并报告拟变化；新问题只用本次报告临时编号，不预占或宣称已分配持久 ISSUE 编号，已有问题仍引用原编号。仅禁止修改项目文件时仍允许维护项目外台账。不可读时不能声称没有已忽略问题；不可写、归属不符或定位失败时继续原审查并说明限制，不假装已保存，也不自动落到项目内。
- 地图更新和台账更新分开执行，建图／重建不得删除或覆盖 `review/`。修改技能本身不生成真实项目台账，不把验证样本或某个游戏的规则写入通用模板。
