# 证据核实与验证

按需读取 V1（审查收尾）、V2（复杂根因）、V3（验证方法）。沿用需求核对记录和问题报告，不另建过程表、不强制运行测试或凑固定数量的假设。

<a id="v1-completion"></a>
## V1 完成条件

对照本次范围核对；简单任务可简记，不扩大为全项目验收。

| 对应流程 | 完成条件 |
|---|---|
| 确定依据、识别项目 | 对象、代码基线、需求与实际入口有据；区分缺失的需求、实现和外部行为 |
| 追踪实现、核对正反路径 | 条款有结论与证据，未查部分有明确缺口；关键副作用追到状态／资源写入、必要提交与失败恢复，不停在接口名、返回值或界面表现 |
| 判断问题是否成立 | 通过下述[问题成立前检查](#v1-reachability)，预期、出错机制与影响构成证据链；已核对可能改变判断的保护，未闭合部分按主文件区分待验证风险与覆盖限制 |
| 验证、报告与台账 | 结论标明静态／运行方式与范围；需求按 [R4](requirements-review-checklist.md#r4-results)核对，问题按主文件及台账规则处理，验证按 V3 核实 |

现有材料能补齐的关键证据先补查；确缺代码、数据、环境或外部契约时，说明缺口、受影响结论与下一步，继续独立可查部分。无文档时依据用户描述和已证实约束，规则不清则保留需求待明确。

本轮可带着未验证项结束，缺口不等于通过，也不必等所有外部条件齐备才交付。浏览过全部文件、测试全通过或没发现问题，都不能代替上述条件。

<a id="v1-reachability"></a>
### 问题成立前检查（所有专项共用）

对准备确认为缺陷的每项结论，核实当前审查版本、平台和数据范围内的以下证据。只追踪会改变该结论的条件；同一入口及生效条件已核实且未变化时复用证据，不为每个问题重复扫描或另建过程表。

| 核实项 | 所需证据 |
|---|---|
| 触发来源 | 玩家操作、启动／后台任务、事件发送或外部回调如何进入目标逻辑；注册、订阅、资源绑定或存在调用代码只能作为线索 |
| 适用条件 | 该路径实际依赖的功能开关、解锁／资格、活动时间／轮次、玩法模式、调度队列、平台／编译分支，以及运行时启用或替代入口 |
| 有效配置 | 查明实际加载来源、选择分支和使用时的有效值；涉及导出、远程覆盖、AB 分流或缓存时核对相关关系，不用注释、默认值或源表代替生效证据 |
| 最终影响 | 在上述条件下，错误是否到达展示、资源／进度、存储、上报或稳定性后果；核对提前返回、覆盖、回退与清理是否改变判断 |

**判定与停止：** 链路闭合即可按影响报告并结束该候选的扩展；有证据排除所报影响时保留数据事实和排除依据。关键条件未知时明确缺口，不把候选升级为确定缺陷；现有材料能补齐的关键证据先补查，缺外部条件时结束该支线并继续独立可查项。搜索未命中或阈值很高，本身不能证明路径永远不可达。

**两个边界：**

- 界面关闭、按钮隐藏或功能入口受限，只约束已核实的那条入口；仍须检查与该影响有关的后台初始化、事件、旧回调和替代入口。UI 不展示不能直接排除后台副作用或崩溃。
- 需求明确要求当前条件下开放功能时，配置或调度使入口无法出现，本身可构成需求偏差。此时核实“应开放的条件 → 实际阻断 → 功能不可用”，不要求先进入被阻断界面，也不将未触达的下游问题一并确认。

**结论联动：** 某入口或生效条件被新证据否定时，同步复核依赖它的其他结论及复现步骤；独立证据仍成立的保留，其余更正状态和计数。对已有运行反馈保留已观察现象，重新核实其版本、条件和根因，不用另一分支的关闭配置否定反馈。

<a id="v2-alternatives"></a>
## V2 替代原因与反证

用于跨模块、时序或 SDK 根因未闭合，反馈与代码冲突，或发现可能推翻原判断的保护时。简单且证据完整的问题直接报告。

- **分开现象与解释。** 观察、日志和执行结果提供现象证据，根因另查；排除某个原因不等于否定用户反馈。
- **核对保护与替代解释。** 沿触发链查相关去重、校验、补偿、统一清理及其他有代码／日志依据的解释。保护须在该时点、条件、对象和范围内有效，仅有函数不能排除问题。
- **选择区分性检查。** 对有依据的候选原因，明确成立时的预期观察及可否定它的证据，优先查能改变结论的源码、状态或日志；实验一次改变一个相关因素，结果按 V3 判断。
- **保留未知。** 缺少反证不等于原因成立；无法区分时说明关键缺口与最小验证方向。继续可做的静态追踪，不以真机复现为门槛。

报告仅保留影响判断的证据、排除理由和缺口，不展开全部假设过程；已排除猜测不作为新问题入台账，正式问题仍按主文件标准判断。

<a id="v3-validation"></a>
## V3 验证有效性

设计／评估方法、引用已有测试或复核修复时，先明确原现象或业务规则。验证权限与源码只读范围沿用主文件。

- **独立预期。** 预期取自需求或明确约束，用可核实的值或性质表达；被测函数返回值、同一错误算法或当前输出不能充当正确性标准。
- **真实后果。** 入口与断言须触及出错机制及相关资源、进度、状态、恢复或统计结果。“不报错”“返回成功”“调用了函数”只作辅助；单一调用者、同步替身或内存模拟不能替代实际竞争、原生生命周期或持久化边界。
- **检错能力。** 明确原错误存在时哪项观察会失败。有可运行的原问题版本时，同一场景先捕获原错误，再对照修复结果。注入错误限隔离样本或已授权测试环境；启动失败、缺依赖、断言未执行不算捕获 Bug。无法确认检错能力时注明，不擅改业务源码凑失败。
- **原场景条件。** 缩小验证保留必要调用关系、状态和时序；修复复核回查原场景及直接受影响的成功／拒绝／恢复分支。小样本通过不代表原流程修好；时序问题记录窗口与运行次数，一次未出现不证明消除。
- **证据范围。** 记录方式、环境、结果与未覆盖项，区分助手实测、用户结果和拟验证步骤。无法运行时继续静态审查并给最小验证方向；静态确认能否关闭仍按[台账规则](issue-tracking.md)，不强制运行验证。

例如重复发奖，应查同一业务的到账增量、领取记录及重试结果；两次展示或接口调用不证明重复到账。去重键、金额与回调顺序以当前项目为准。

测试覆盖不足只说明验证缺口，不自动构成玩家 Bug；业务缺陷仍需实现证据。平台专项验证见 [C4](stability-sdk-review-checklist.md#c4-validation)。
