# 证据核实与验证

用于判断审查能否收尾、复杂问题的根因是否成立，以及验证能否支持结论。只读当前需要的 V1／V2／V3；沿用现有需求核对记录和问题报告，不另建过程表，不强制运行测试或列固定数量的假设。

<a id="v1-completion"></a>
## V1 完成条件

形成结论前，对照本次任务范围检查下列条件；简单任务可简记，不扩大成全项目验收。

| 对应流程 | 可以形成结论的条件 |
|---|---|
| 确定依据、识别项目 | 审查对象、代码基线、相关需求与实际入口有据；缺失的需求、实现或外部行为已区分 |
| 追踪实现、核对正反路径 | 本次范围内的条款有结论与证据，未核对部分有明确缺口；相关关键副作用追到实际状态／资源写入、必要的提交及失败恢复，而非停在接口名、返回值或界面表现 |
| 判断问题是否成立 | 可达入口、触发条件、预期依据、出错机制与所述影响能连成证据链；可能改变结论的已有保护已核对，未闭合部分按主文件区分待验证风险或覆盖限制 |
| 验证、报告与台账 | 结论注明静态／运行方式及适用范围；需求核对使用 [R4](requirements-review-checklist.md#r4-results)，问题与状态按主文件和台账规则处理，验证结果按 V3 核实 |

能用现有材料补齐的关键证据先补查；确实缺少代码、数据、环境或外部契约时，写清缺什么、影响哪项结论以及下一步核实方向，继续其余检查。无需求文档时按用户描述和已证实约束判断，规则不明确的部分保留为需求待明确。

“本轮审查结束”可以包含尚未验证的部分；已定位缺口不等于相关功能通过，也不要求先消除所有外部限制才能交付已有结论。仅浏览所有文件、测试全部通过或未发现问题，都不能替代上述条件。

<a id="v2-alternatives"></a>
## V2 替代原因与反证

用于跨模块、时序或 SDK 问题的根因尚未闭合，或反馈与代码证据不一致、出现可能推翻原判断的保护机制时。简单且证据完整的问题直接形成结论，无需凑出多个原因。

- **分开现象与解释。** 用户观察、日志记录和实际执行结果属于现象证据；哪个机制导致它需要另行核实。某个根因被否定，不自动否定用户反馈的现象。
- **核对能改变判断的证据。** 沿实际触发链检查去重、校验、补偿、统一清理等相关保护，以及其他有代码或日志依据的解释。保护是否有效要核对执行时点、条件、对象与覆盖范围；仅看到保护函数存在也不足以排除问题。
- **选择能区分原因的检查。** 对仍有依据的候选原因，说明若成立应观察到什么，以及哪项证据会否定它；优先检查能改变结论的源码分支、状态或日志。需要实验时一次只改变一个相关因素，按 V3 核对观察结果。
- **证据不足时保留未知。** 缺少反证不等于已证明原因；两种解释尚无法区分时，说明关键缺口和最小验证方向。现有材料能继续静态追踪时继续，不以必须先真机复现作为审查门槛。

报告只保留影响判断的证据、排除理由及剩余缺口，不展开全部假设过程。已排除猜测不作为新问题写入台账；正式缺陷与具体风险仍按主文件标准判断。

<a id="v3-validation"></a>
## V3 验证有效性

设计或评估验证方法、引用已有测试结果、复核修复时使用。先明确要验证的原现象或业务规则，再判断方法是否真的能识别它；验证权限与业务源码只读范围沿用主文件。

- **预期独立于被测实现。** 从需求或明确业务约束得到预期，使用可核实的具体值或性质。把被测函数的返回值、同一错误算法或当前实际输出当作标准答案，不能验证规则正确性。
- **观察真实后果。** 选择能到达出错机制的入口与断言，检查相关资源、进度、状态、恢复或统计结果。只确认“不报错”“返回成功”“某函数被调用”不足以证明对应业务结果正确；它们可作辅助证据。单一调用者、同步替身或内存模拟不能代替实际涉及的竞争、原生生命周期或持久化边界。
- **确认方法有检错能力。** 说明原错误仍存在时哪项观察会失败。有可运行的原问题版本时，用相同场景验证能捕获原错误，再对照修复后的结果；必要的错误注入只在隔离样本或已获授权的测试环境进行。启动失败、缺依赖或断言未执行不算成功捕获原 Bug。无法验证检错能力时保留这一限制，不为凑出失败擅自改业务源码。
- **保持原场景的关键条件。** 缩小验证范围时保留触发问题所需的调用关系、状态和时序；修复复核还要回查原场景及直接受影响的成功／拒绝／恢复分支。仅缩小样本通过不能证明原流程修好；时序问题说明观察窗口和运行次数，一次未出现不证明风险消除。
- **结论限定在实际证据内。** 记录执行方式、环境、结果及未覆盖边界，区分助手实测、用户提供的结果与拟验证步骤。没有运行条件时继续静态审查，并给最小验证方向；静态确认可否关闭问题仍以[台账关闭规则](issue-tracking.md)为准，不强制所有问题做运行验证。

例如“重复回调导致重复发奖”，需要观察同一笔业务的实际到账增量和领取记录，并核对重试后的结果；展示两次或奖励接口被调用两次本身不能证明重复到账。此例只说明检验方法，具体去重键、奖励数量与允许的回调顺序以当前项目为准。

现有测试没有覆盖某条规则，是该验证的能力缺口，不自动成为玩家 Bug；发现业务错误仍需实际实现证据。SDK／目标平台的专项验证见 [C4](stability-sdk-review-checklist.md#c4-validation)。
